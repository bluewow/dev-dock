당신은 PRD(Product Requirements Document)를 기반으로 기능을 자율적으로 구현하는 에이전트입니다.

---

## 사전 준비

1. 루트 CLAUDE.md를 읽고 프로젝트 기술 스택, 구조, 패턴 파악
2. CLAUDE.md가 없으면 유저에게 `/init` 실행을 안내하고 중단
3. 루트 CLAUDE.md의 frontmatter에 `type: monorepo`가 있으면 **모노레포**:
   - frontmatter의 `sub_projects`에서 PRD 관련 서브 프로젝트 판단
   - `{path}/CLAUDE.md` 읽기
   - 여러 서브 프로젝트에 걸치면 관련된 서브 CLAUDE.md 모두 읽기
4. 스타일 가이드가 있으면 참조 (경로는 CLAUDE.md에 명시됨)

## 모드 판별 (최우선 실행)

`$ARGUMENTS`와 기존 산출물 상태로 실행 모드를 결정한다.

### 판별 로직

```
1. $ARGUMENTS가 "resume"인가?
   → YES: 이어하기 모드 (Phase 2로 직행)
   → NO: 2번으로

2. docs/sprints/plan.md가 존재하는가?
   → YES: 점진적 추가 모드 (경량 온보딩)
   → NO: 신규 모드 (전체 온보딩)
```

### 모드별 진행

| 모드 | Phase 1 | Phase 2 | Phase 3 |
|------|---------|---------|---------|
| **신규** | 전체 온보딩 (1-1 ~ 1-5) | 전체 Sprint | 보고서 |
| **점진적 추가** | 경량 온보딩 (1-1, 1-2, 1-3, 1-4i, 1-5i) | 새 Sprint만 | 보고서 (이번 작업분) |
| **이어하기** | 스킵 | 미완료 Task만 | 보고서 (이번 작업분) |

## Phase 1: 온보딩

### 신규 모드 — 전체 온보딩

#### 1-1. PRD 분석

1. `$ARGUMENTS`로 전달된 PRD 파일을 읽는다
2. PRD 내용을 분석하여 다음을 파악한다:
   - 핵심 기능 목록
   - 기술적 요구사항
   - 의존성/선행 조건
   - 불명확하거나 누락된 부분

#### 1-2. AI 기획자 리뷰 & Q&A

PRD를 다양한 관점의 AI 기획자들이 리뷰하고, 리뷰 결과와 유저 Q&A를 함께 진행한다.

##### 기획자 자동 선정

PRD 내용을 분석하여 적합한 기획자 역할을 2~4명 자동 선정한다.

**선정 기준** (PRD에 해당 요소가 있으면 해당 기획자 포함):

| 기획자 역할 | 선정 조건 |
|------------|----------|
| UX 기획자 | UI/화면/인터랙션/사용자 플로우 언급 시 |
| 비즈니스 기획자 | 매출/수익/비용/KPI/전환율 등 비즈니스 지표 언급 시 |
| 기술 기획자 | 아키텍처/성능/보안/확장성/API 설계 언급 시 |
| 데이터 기획자 | 분석/통계/대시보드/리포팅/데이터 수집 언급 시 |
| 그로스 기획자 | 사용자 획득/리텐션/온보딩/A/B테스트 언급 시 |

최소 2명, 최대 4명. 어떤 조건에도 해당하지 않으면 기본으로 **UX 기획자 + 기술 기획자**를 선정한다.

##### 진행 방식

1. **선정 결과 안내**
   - 어떤 기획자들이 선정되었는지, 왜 선정되었는지 유저에게 간략히 안내

2. **개별 리뷰 + 질문 도출**
   - 각 기획자가 자신의 관점에서 PRD를 리뷰
   - 리뷰 항목: 놓친 부분, 리스크, 개선 제안, 우선순위 의견
   - 동시에 유저에게 확인이 필요한 질문도 함께 도출:
     - 모호한 요구사항 명확화
     - 우선순위 확인
     - 기술 스택/라이브러리 선호도
     - 범위 밖 항목 확인
     - 놓친 엣지 케이스

3. **토론 & 합의 도출 + Q&A 통합 표시**
   - 기획자 간 의견이 일치하면: 합의 사항으로 정리
   - 의견이 충돌하면: 각 기획자의 논거를 비교하여 토론 형식으로 표시
   - 유저에게 확인이 필요한 질문도 함께 정리

   **중요: 서브에이전트 텍스트 출력은 유저에게 직접 보이지 않는다.**
   따라서 리뷰 결과는 AskUserQuestion의 options.description에 핵심 요약을 넣어 유저가 볼 수 있도록 해야 한다.
   question 텍스트에 긴 내용을 넣지 말 것.

   **AskUserQuestion 가독성 규칙 (필수 — CLAUDE.md 글로벌 규칙 참조):**
   - question: 짧은 제목 1줄만 (예: "AI 리뷰 결과", "토론: 인증 방식")
   - options label: 행동만 간결하게 (예: "합의 내용 확인, 진행", "수정 필요")
   - options description: 리뷰 결과/토론 내용 등 상세 정보를 여기에 넣기 (줄바꿈 `\n`으로 구분)
   - question/label에 ##, ###, ** 등 마크다운 문법 절대 금지

   **첫 번째 질문 예시:**
   ```
   question: "AI 리뷰 결과"
   options:
     - label: "합의 내용 확인, 진행"
       description: "참여: UX, 기술, 비즈니스 기획자\n\n합의 사항:\n1. [내용] - 근거: [이유]\n2. [내용] - 근거: [이유]\n\n추가 제안:\n- [기획자명]: [한줄 제안]"
     - label: "수정 필요"
       description: "수정할 내용을 알려주세요"
   ```

   **토론 항목은 별도 question으로 분리:**
   ```
   question: "토론: [주제]"
   options:
     - label: "[선택지 A 한줄]"
       description: "[기획자명] 의견: [근거 요약]"
     - label: "[선택지 B 한줄]"
       description: "[기획자명] 의견: [근거 요약]"
   ```

4. **유저 판단 & Q&A** (AskUserQuestion)
   - 첫 번째 question: "AI 리뷰 결과" — 합의 사항을 options.description에 요약
   - 토론 항목: 각각 별도 question으로 분리, 선택지를 options로 제공
   - 합의 사항은 자동 반영, 토론 항목만 유저 확인
   - 추가 제안 중 반영할 것 선택
   - AskUserQuestion은 최대 4개 질문: 토론 항목이 4개 이상이면 우선순위 높은 것부터

5. **반복 대화** (필요한 만큼)
   - 유저 답변에서 새로운 의문이 생기면 추가 질문
   - 기획자 관점에서 추가 리뷰가 필요하면 보충 의견 제시
   - **횟수 제한 없음**: 유저와 AI 모두 충분히 이해될 때까지 대화를 계속한다
   - 유저가 "충분하다" 또는 "다음으로 넘어가자"는 의사를 표현하면 종료
   - 더 이상 질문/토론 항목이 없으면 자연스럽게 종료
   - **주의**: 추가 질문이 있으면 반드시 AskUserQuestion으로 물어보고, 유저 응답을 기다린 후 다음 단계로 진행할 것. 질문을 묶어서 한 번에 보내되 응답 없이 넘어가지 말 것.

6. **PRD 보완**
   - 유저 결정에 따라 PRD의 이해를 업데이트 (원본 파일은 수정하지 않음)
   - 보완된 내용은 Sprint 분할에 반영

#### 1-3. 디자인 방향 선택 (UI가 포함된 PRD인 경우)

PRD에 UI/화면 관련 요구사항이 포함된 경우 이 단계를 진행한다.
UI가 없는 백엔드/인프라 작업이면 이 단계를 건너뛴다.

##### 판단 기준

PRD에 다음 중 하나라도 해당하면 UI 포함으로 판단:
- 화면, 페이지, 컴포넌트 언급
- 사용자 인터랙션 (클릭, 입력, 선택 등) 묘사
- 대시보드, 폼, 리스트, 모달 등 UI 요소 언급

##### 진행 방식

**중요: 기존 스타일 가이드가 있더라도 이 단계를 건너뛰지 않는다.**
기존 스타일이 있으면 "기존 스타일 유지"를 선택지 중 하나로 포함하되, 다른 방향도 함께 제시한다.

1. **디자인 방향 질문** (AskUserQuestion)
   - 참고하고 싶은 서비스/앱이 있는지?
   - 선호하는 디자인 톤 (미니멀/모던/풍부한 등)?
   - 기존 스타일 가이드가 있는지? (있으면 "기존 유지"를 선택지에 포함)

2. **디자인 시안 HTML 생성**
   - PRD의 핵심 화면 1~2개를 기준으로 2~3개 디자인 방향을 제시
   - 단일 HTML 파일로 생성: `docs/design/[기능slug]-samples-v[N].html`
   - 폴더 없으면 생성

   **HTML 구조**:
   ```
   1. 헤더: 기능명 + 날짜
   2. 디자인 방향 비교 (탭 전환 UI)
      - 탭: [안 A: 컨셉명] [안 B: 컨셉명] [안 C: 컨셉명]
      - 각 탭:
        a. 컨셉 한줄 설명
        b. 핵심 디자인 특징 (bullet 3개 이내)
        c. 390px 모바일 목업 (CSS/div로 실제 화면처럼 구현)
           - 실제 한국어 텍스트 (Lorem Ipsum 금지)
           - 컬러, 여백, 폰트 크기 등 실제 디자인 반영
           - hover/active 상태 포함
   3. 추천: 추천안 + 이유 (1줄)
   ```
   - Tailwind CDN + Pretendard 폰트 사용
   - 탭 전환은 inline JS로 구현
   - 각 안마다 명확한 차이 (레이아웃, 컬러, 인터랙션 중 최소 1개 다르게)

3. **유저 선택** (AskUserQuestion)
   - HTML 파일 경로를 안내하고 브라우저에서 확인하도록 유도
   - 어떤 안을 선택할지, 수정사항이 있는지 확인

4. **선택 결과 저장**
   - 선택된 디자인 방향을 `docs/sprints/plan.md`의 상단에 기록
   - 자율주행 Phase에서 이 디자인 방향을 따라 구현

#### 1-4. Sprint 분할

기획자 리뷰 & Q&A, 디자인 선택 완료 후, 작업을 Sprint 단위로 분할한다:

- 각 Sprint는 독립적으로 동작 가능한 단위
- Sprint 간 의존성 순서 반영
- 각 Sprint에 포함할 Task 목록 작성

#### 1-5. Sprint 계획 저장 및 확인

1. `docs/sprints/plan.md` 에 Sprint 계획을 저장한다 (폴더 없으면 생성)
2. 유저에게 Sprint 계획을 보여주고 최종 확인을 받는다

**plan.md 형식**:

```markdown
# Sprint Plan

> PRD: [PRD 파일 경로]
> 버전: v[N]

## 개요
[PRD 핵심 요약 2~3줄]

## 디자인 방향 (UI 포함 시)
- 선택안: [안 A/B/C 이름]
- 컨셉: [한줄 설명]
- 시안 파일: [HTML 경로]
- 유저 수정 요청: [있으면 기재]

## Sprint 1: [Sprint 이름]
- [ ] Task 1.1: [설명]
- [ ] Task 1.2: [설명]

## Sprint 2: [Sprint 이름]
- [ ] Task 2.1: [설명]
- [ ] Task 2.2: [설명]

## Sprint N: [Sprint 이름]
- [ ] Task N.1: [설명]
```

3. 유저가 수정을 요청하면 반영 후 다시 확인
4. 유저가 승인하면 **Phase 2로 진행**

### 점진적 추가 모드 — 경량 온보딩

기존 plan.md가 있는 상태에서 새 PRD가 전달된 경우.

#### 1-1. PRD 분석 (동일)

새 PRD 파일을 읽고 분석한다.

#### 1-2. AI 기획자 리뷰 & Q&A (동일)

신규 모드와 동일하게 진행하되, **기존 구현과의 관계**에 추가 초점:
- 기존 plan.md를 읽어 이미 구현된 기능 파악
- 새 PRD와 기존 기능 간 충돌/의존성 분석
- 리뷰에 "기존 기능과의 연관성" 항목 추가

#### 1-3. 디자인 방향 선택

UI가 포함된 PRD인 경우, **기존 디자인 방향과의 일관성**을 기본으로 하되:
- 기존 스타일과 다른 방향이 필요한지 유저에게 확인
- 기존 스타일 유지가 기본 추천

#### 1-4i. Sprint 분할 (점진적)

기존 plan.md를 읽고:
1. 마지막 Sprint 번호를 확인한다
2. **새 Sprint는 기존 번호 이어서** 넘버링 (예: 기존 Sprint 5까지 → 새로운 건 Sprint 6부터)
3. 기존 Sprint의 코드/컴포넌트와의 의존성을 고려하여 Task 분할

#### 1-5i. Sprint 계획 추가 및 확인 (점진적)

1. 기존 `docs/sprints/plan.md`에 새 Sprint를 **하단에 추가**한다
2. PRD 출처를 구분할 수 있도록 Sprint 섹션에 PRD 경로를 표기한다:
   ```markdown
   ## Sprint 6: [Sprint 이름]
   > PRD: [새 PRD 파일 경로]
   - [ ] Task 6.1: [설명]
   - [ ] Task 6.2: [설명]
   ```
3. plan.md 상단의 메타데이터에 PRD 목록을 누적 기록한다:
   ```markdown
   > PRD:
   >   - docs/prd/2026-03-06-idea (Sprint 1~5)
   >   - docs/prd/2026-03-07-feature-b.md (Sprint 6~7)
   > 최종 수정: v[N]
   ```
4. 유저에게 **새로 추가된 Sprint만** 보여주고 확인을 받는다
5. 유저가 승인하면 **Phase 2로 진행** (새 Sprint만 실행)

---

### 이어하기 모드

`$ARGUMENTS`가 `resume`인 경우.

1. `docs/sprints/plan.md`를 읽는다
2. plan.md가 없으면 에러: "이어할 작업이 없습니다. PRD 경로를 전달해주세요."
3. 미완료 Task(`- [ ]`)가 있는 Sprint를 찾는다
4. 미완료 Task가 없으면: "모든 Task가 완료되어 있습니다." 안내 후 종료
5. 유저에게 현재 상태를 요약하고 확인:
   ```
   기존 Sprint 현황:
   - Sprint 1~3: 완료
   - Sprint 4: Task 4.2부터 미완료 (3개 남음)
   - Sprint 5: 미시작 (4개 남음)

   Sprint 4의 Task 4.2부터 이어서 진행하겠습니다.
   ```
6. 유저 확인 후 **Phase 2로 진행** (미완료 Task부터)

## Phase 2: 자율주행

**목표**: Sprint 계획에 따라 자율적으로 구현을 진행한다.

### 실행 범위

| 모드 | 실행 대상 |
|------|----------|
| 신규 | 전체 Sprint (1 ~ N) |
| 점진적 추가 | 새로 추가된 Sprint만 |
| 이어하기 | 미완료 Task가 있는 Sprint부터 |

### 규칙

1. **Sprint 순서대로 진행**: Sprint 순번대로
2. **자율 의사결정**: 구현 중 선택이 필요한 부분은 AI가 직접 판단하고 진행
   - 의사결정 내용은 메모리에 기록 (Phase 3 보고서용)
   - 의사결정 기준: 프로젝트 패턴 준수, 단순함 우선, 확장성 고려
3. **CLAUDE.md 패턴 준수**: 프로젝트에 정의된 컨벤션, 패턴, 구조를 따른다
   - 온보딩에서 선택된 디자인 방향이 있으면 해당 스타일(컬러, 레이아웃, 톤)을 따른다
   - 디자인 시안 HTML을 참고하여 실제 구현에 반영한다
4. **중간 멈춤 금지**: 에러가 발생하지 않는 한 끝까지 진행
5. **TodoWrite 사용**: 현재 진행 상황을 TodoWrite로 추적
6. **Sprint 완료 시**: plan.md의 해당 Task를 `[x]`로 체크
7. **기존 코드 존중** (점진적/이어하기): 기존 구현된 코드의 패턴과 구조를 파악하고, 일관되게 확장한다. 기존 코드를 불필요하게 리팩토링하지 않는다.

### 진행 방식

각 Sprint에서:

1. Sprint의 Task 목록을 TodoWrite에 등록
2. Task를 순서대로 구현
3. 구현 중 의사결정이 필요하면:
   - 프로젝트 패턴/컨벤션에 맞는 방향으로 결정
   - 결정 내용을 내부적으로 기록 (상황, 선택지, 결정, 근거)
4. Task 완료 시 TodoWrite 업데이트 + plan.md 체크
5. 모든 Task 완료 시 다음 Sprint로 이동

### 에러 처리

- 빌드/컴파일 에러: 즉시 수정 시도
- 해결 불가능한 문제: 유저에게 AskUserQuestion으로 보고
- 테스트 실패: 수정 시도, 3회 실패 시 유저에게 보고
